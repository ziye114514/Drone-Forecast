# 当前缺口的已有解法与GPU改造路线（2026-11-01）

范围：阅读论文原文、作者仓库、官方文档及本地源码/历史记录；本轮没有改运行算法，没有训练、RAW负载实验或FPS测速。GPU型号仅通过nvidia-smi查询：RTX 5060 Laptop GPU，8151 MiB显存。论文数字不是本机复现成绩，建议不是已经获得的收益。

## 1. 结论和优先次序

1. 先修有效状态之前的校准采样，以及过去0.2秒位移残差与当前加速度的时间含义。最大坏例主要受未知残差项影响，不能归因于未验证的某次谐波错误。
2. 保留纯ON/OFF和五圆/部分桨/侧视逻辑。周期筛选与原生轮廓恢复应有不同资格；不能把周期确认像素当作完整物理桨缘。
3. 当前已经使用GPU做周期估计。需要将更多前处理和支撑恢复串在同一设备端，减少CPU全幅展开、拷贝和往返；只加一个CUDA调用不能解决30Hz。
4. 跟踪阶段维护相位/频率/变化率和候选置信度，发现或失锁阶段再作较宽频谱搜索。不能用永远选旧峰的方法制造平稳。
5. 三种可见性使用同一个中心/速度状态和不同测量模型；隐藏桨的位置先验不能成为隐藏桨的实测周期。主线仍是用户的五圆和二力机制。

## 2. 未知作用：已有扰动观测器，而非任意位置误差直接补加速度

### 已有实现

- ETH ASL的mav_control_rw包含Kalman外扰观测器：联合预测/更新状态和协方差，并对估计外力/力矩作边界约束。
  - 仓库：https://github.com/ethz-asl/mav_control_rw
  - 直接源码：https://github.com/ethz-asl/mav_control_rw/blob/master/mav_disturbance_observer/src/KF_disturbance_observer.cpp
- PX4 EKF2把观测放在延迟融合时间线上处理，再将历史状态向当前时刻传播；不同传感器观测带时间戳并由FIFO缓冲。它也对创新进行统计检查。
  - 官方文档：https://docs.px4.io/main/en/advanced_config/tuning_the_ecl_ekf

### 适配本项目

研究状态可采用二维p、v、合并未知加速度d；q*n作为有不确定度的控制输入。有效增益k慢更新，未知项d通过状态估计更新，而非直接覆盖当前净加速度。

如果继续使用积分残差，应保留积分的起止时间、期间输入和初始速度不确定度。它是整个区间的观测，不应自动被当成当前瞬时外力。历史状态的更正只用截止当前已到达的信息，再传播到现在；不等候未来数据发布当前预测。

必须先修当前实现允许state.valid=False时将p/v放入pending的路径。位置/速度尚未可靠，不能用于解释未知力。重新锁定或参考中心变化应重新处理协方差和偏置，避免把参考变化算成物理加速度。

边界：ETH/PX4原系统有机载状态或IMU/控制输入；本项目只借用观测器、时间戳和协方差机制，不能直接搬完整参数、宣称同样收敛，也不要求用户补采机载日志。图像d仍是px/s²的合并项，包含物理作用和投影/观测误差。

本地证据：gaps_explained/diagnosis.json；110.4s当前中心误差约0.84px，未知水平项+1089px/s²，开启分支0.4s误差157.33px，关闭62.34px。三次force.active发生在位置状态未有效阶段。确切物理误差来源仍无独立真值。

## 3. 周期跳变：保留相位和多候选，避免单窗赢家直接平方

### HelixTrack（作者代码，本机早已有）

- 论文：https://arxiv.org/abs/2603.09235
- 作者仓库：https://github.com/radimspetlik/helixtrack
- 本地：D:/drone forecast/helixtrack-main

作者将事件反投影到转子平面，逐事件更新相位、角速度、角加速度，并由批量Gauss-Newton更新几何。这样频率有跨时刻状态，几何与相位能相互约束。它仍需要初始化，近乎成线时平面反解会病态，不能用来强恢复所有侧视。

必须继承本地历史：10月25日已实际编译作者核心并做过ABI适配。移动ROI后连续支持改善，但自然退化后失锁，旁路仍很慢；10月27日共享空间相位也已有模块，尚无稳定预测收益。不要把“首次接入HelixTrack”列作新工作。参见OPTIMIZATION_JOURNAL_20261025.md、OBSERVATION_EXTENSION.md、SHARED_ANGULAR_PHASE.md。上游当前根目录未见完整许可证，现有作者代码/DLL继续限本机研究，不进入发布包。

下一步可复用现有状态接口，将候选f、f/2、2f的观测支持与预测相位分别评估；无法分辨时保留不确定度，暂缓增益学习。不得把同一周期像素源之间的互相一致当作独立RPM真值。

### FrequencyCam（低计算量的周期备选）

- 论文：https://arxiv.org/abs/2211.00198
- 作者仓库：https://github.com/ros-event-camera/frequency_cam
- 本地：D:/drone forecast/frequency_cam-master

每个像素维护小状态，用IIR滤波及零交叉间隔更新周期；已有完整周期时不会随便被半周期覆盖，过期状态会失效。C++头文件updateState可直接审阅，不需要重写ROS框架。

它内部包含近似亮度状态。用户的无G重建边界继续有效，本轮不引入它的亮度图，也不未经消融替换纯ON/OFF引擎。可先借鉴逐事件更新、完整/半周期资格和超时机制；固定传感器像素上的状态还会受到目标平移和多桨重叠影响。

既有中位最近候选规则已被阶跃试验证明可能锁死；不能再把散布减小当成跟踪成功。已有ConsensusFrequencySelector也有10%死区和约2帧阶跃滞后，不能只报告平滑程度。

### EV-Tach的角色

https://arxiv.org/html/2209.02205v1

它用空间聚类和时空ICP配准估计旋转，不等于直接从事件数求RPM。本地有限适配已经失败于合成高转速和真实桨盘一致性且很慢（RPM_RECALL_20261031.md）；不能重复把它当成现成准确测速模块。论文成果和本地不完整复现应区分。

## 4. 桨叶筛选和轮廓：先找旋转支撑，再用原生事件估形状

### DDHF

https://arxiv.org/html/2603.08386v1

论文以GPU批量NDFT和谐波梳状指纹筛选像素；噪声底使用中位数，考虑同像素多个桨的频谱。它在0度仰角例子失败，图中某些姿态只识别桨盘内部。因此“旋转证据”不等于“完整边界”，严格侧视没有被普遍解决。论文报告2.39ms窗口处理延迟、NVIDIA L40-8Q；任务和硬件与本项目不同，不能换算成本机完整预测FPS。本次检索未确认其可直接下载的官方实现，不把arXiv的Report GitHub Issue当作代码。

### effqpdet：更贴近纯ON/OFF的直接候选

https://github.com/radimspetlik/effqpdet

SCIA2025作者C++实现。对空间块的事件间隔作Poisson突发检测，以突发间隔估转速，并以累计事件拟合椭圆。对本项目的价值是低成本定位候选支撑，再对候选作较严格周期验证；候选检出仍不保证获得完整物理桨盘。

代码依赖C++17、Metavision、Boost、HDF5等并含作者路径。不能称Windows pip即用，不能拿作者实时因子当本机速度。若移植只处理小核心，发布前逐文件保留许可证和引用，本轮未复制第三方源码进产品。

### AAMED：弧段组装的备选

https://github.com/Li-Zhaoxi/AAMED

它利用弧邻接关系产生椭圆候选，提供C++及Python入口，可减少本项目逐帧从所有碎片重猜的代码量。仓库标GPL-2.0，本轮仅研究；不要随意混入现有发行包。它不能从几乎直线且有厚度的片段唯一恢复桨径，也不是作者已验证的事件相机侧视解法。

推荐保留当前“两级证据”：周期确认作为高可信种子；与其相连且满足方向/形状/时间一致性的原生ON/OFF作为轮廓候选。候选不自动升级为周期实测。轮廓继续在当前真实像素上估计，不将膨胀边界当物理桨缘。

## 5. 可见性切换与中心：共享状态，不让模式换一个运动原点

原最接近论文Relative State Estimation using Event-Based Propeller Sensing已将频率、姿态和位置KF耦合，并以Norfair维持短时漏检轨迹；采用yaw-free姿态分解。

https://arxiv.org/html/2604.18289v1

但它使用已知质量、推力系数、物理对角尺寸及观测者位姿等条件，主要实验四桨可见；不能直接宣称解决本项目未知参数和两桨侧视。其检测ROI、逐桨跟踪、频率平滑和耦合状态机制可借用。

本项目应保持同一中心/速度状态，four/three/partial/axis作为不同观测模型：四桨更新共享平面；部分桨只更新可观测维度、保留缺失项先验；成线更新线方向和可观测中心分量，法线符号维持多假设/历史资格。侧视不要求恢复四个桨，补出的中心点不补真实转速。

权重可借FilterPy IMM框架，但标准IMM要求相同状态维度和一致的状态含义，并不自带五圆测量模型。将各模式嵌入相同状态后，才可由当前测量似然更新模式概率。不能任意平均不同坐标原点的状态。

https://github.com/rlabbe/filterpy/blob/master/filterpy/kalman/IMM.py

另一个有价值的对照是Event-Only Drone Trajectory Forecasting with RPM-Modulated Kalman Filtering：它用周期调节过程噪声而非强行标定绝对推力，评估时使用历史人工框位置，不能当成完整检测结果。可作“周期只增加机动不确定度”的单独对照，不能悄悄替代用户的力学主线。

https://arxiv.org/html/2603.01997v1

## 6. FPS：已有GPU，瓶颈是整个数据路径

### 已核对的当前实现

- predictive_harmonics_cuda.py：NumPy在CPU筛选、bincount、排序和分组；Torch在GPU计算频谱/验证；多次cpu().numpy()返回稀疏结果，CPU再生成全幅图。
- rotor_period_worker.py：SDK Python3.11与CUDA Python3.13通过常驻进程及共享内存通信。mask/frequency/evidence三张1280x720全幅图合计约8.29MB，每次还有共享内存赋值和父进程copy。
- len(events)>200000会退回CPU周期估计，存在高事件率窗口的长尾风险。仅源码风险，本轮没有测其出现次数。
- rotor_support_front.py：事件累积、密度和空间支撑仍有CPU全幅操作。
- rotor_only_front.py：原生重建中的高斯、形态学和连通域为CPU OpenCV；小规模椭圆和状态更新亦在CPU。
- 当前父进程同步等待工作进程。readline等待不等于纯通信开销，它包含等待CPU/GPU服务完成。

已有整段保存结果：clear核心耗时中位232.91ms/P95 283.11ms，side 212.55/441.02ms；核心处理能力约3.9FPS。30Hz预算为33.33ms。CPU初版约1.16FPS到CUDA+空间优化约3.92FPS的变化有多项改动，不能全归GPU。

单次cProfile样本（非稳态均值）：step277ms，周期往返64ms、原生重建48ms、累积29ms、几何26ms、平移19ms；父子函数含嵌套，不能把整张profile各行相加。即使整个周期调用假设降至0，277-64=213ms，仍约4.7FPS，说明仅优化该调用不足以到30Hz。

### 能直接使用的GPU工具

- NVIDIA CUDA Best Practices建议减少主机/设备传输，使中间数据留在设备，批量传输，并在适合时用固定页内存与异步流重叠。
  https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html
- CuPy已有ndimage高斯滤波和连通域接口；label本身可能同步设备，不能假设换名就一定更快。
  https://docs.cupy.dev/en/stable/reference/generated/cupyx.scipy.ndimage.gaussian_filter.html
  https://docs.cupy.dev/en/stable/reference/generated/cupyx.scipy.ndimage.label.html

### 建议实现顺序

1. 先改接口：周期结果保留稀疏像素/候选和目标局部支撑；避免每帧三张全幅结果在CPU与共享内存间重复展开/复制。记录事件数、回退路径和观测年龄。
2. 将事件累积、密度筛选、像素分组/频谱、种子支撑恢复串在同一GPU工作进程；中间数组常驻并复用。SDK解码进程可继续独立，只传一次原生事件，不要求更改系统Python。
3. 轮廓回CPU时只返回目标局部像素/小图；少量椭圆、中心状态和扰动KF先留CPU。小矩阵不值得单独搬GPU。
4. 将每帧宽频扫改为“发现/失锁较宽搜索，已跟踪目标窄频和相位更新”，保留周期性全局重发现。不能为提速丢掉失锁重捕能力。
5. 解码、GPU和输出用有界流水线；队列满时明确丢弃过期任务或重新同步，记录被跳过的观测，禁止无限排队后把陈旧预测称实时。
6. 两项指标同时计：持续的新观测/有效预测更新率，以及采集截止到结果可用的P95延迟。30Hz发布定时器重复旧预测不算30Hz检测。

这是有根据的改造路线，尚未证明在本机可持续30Hz。更换显卡不是当前优先项；算法可观测性、谐波歧义和残差含义也不能由GPU算力消除。
